# DTR-REQ-030AG: pre-outcome paired-model development screen

**State:** `req030ag-development-20260929-v3` is the immutable prospective design being validated for dispatch; no model episode has run. This is not a result, a CONFIRM release, or authorization for a full benchmark.

## Scientific question and boundary

The immediate unresolved empirical gate is whether the already-pinned Qwen2.5-Coder 7B/14B pair can resolve a useful, nontrivial share of an eight-task, eight-repository-family development cohort under one common HF/BF16/B200 agent contract. This is a competency/feasibility screen only. It cannot estimate a target-population success rate, establish superiority of one model, identify an H/P router effect, or tighten the fixed-benchmark interval. The tasks are eight selected issues, not a representative sample. Results will be descriptive and used only to decide whether a separately designed next comparison is worth specifying.

The screen is selected from the first eight queue entries after the prior frozen Seaborn row in the source-bound REQ009 component queue, ranks 5–12, with one distinct family per row. The fixed tasks are `psf__requests-2931`, `pydata__xarray-3151`, `pylint-dev__pylint-8898`, `pytest-dev__pytest-6202`, `scikit-learn__scikit-learn-13328`, `sphinx-doc__sphinx-8269`, `sympy__sympy-19954`, and `astropy__astropy-14365`. Dataset, queue, M01 eligibility/content, test/reference bundle, task image leaf digest, base commit and public projection are pinned in the release manifest. No substitution, exposed-task retry, prompt tuning, or outcome-driven rerun is allowed.

## Frozen treatment and execution

The pair is `Qwen/Qwen2.5-Coder-7B-Instruct` at `c03e6d358207e414f1eca0bb1891e29f1db0e242` and `Qwen/Qwen2.5-Coder-14B-Instruct` at `aedcc2d42b622764e023cf882b6652e646b95671`; both are Apache-2.0. Both use the same pinned Qwen 7B tokenizer, Yale module `PyTorch/2.9.1-foss-2024a-CUDA-12.8.0` (Python 3.12.3, PyTorch 2.9.1, CUDA 12.8, Jinja2 3.1.4), Transformers 4.51.3, one B200, BF16, SDPA, greedy decoding, a 16,384-token context, 1,536 new-token ceiling, 24 logical calls, one fixed prompt, one task attempt/model attempt, and 45 minutes maximum per episode. Tool commands have a 60-second cap; retained action and output are byte-capped. Source/package, wheel, task image, evaluator, runner, adapter, prompt, model files and runtime identities are SHA-256 bound. The execution receipt records actual resource/runtime/device, model load and peak memory, per-call token/timing/finish data, tool actions/bytes, patch, grades, failure class and cleanup.

Before any model assets are downloaded or either model loaded, the job validates the exact Python/CUDA/package/wheel runtime, verifies all eight task OCI image pins and base checkouts, exports bounded task source snapshots, then executes baseline and reference controls exactly once for all eight tasks in the same isolated evaluator path. Every control must have the expected markers, complete declared-status set and frozen outcome: baseline has all declared F2P checks fail and P2P checks pass; reference has every declared check pass. A failed/missing control or image/source/runtime check stops the cohort before model weights are downloaded. This control block is one task's control per row, not an independent 250-task evaluation.

Only after that gate passes are the exact two model snapshots obtained and verified. Each of the eight tasks then receives exactly one episode from each model (16 total); model order is deterministically SHA-256 ranked and balanced 4/4. The model API receives only the pinned public problem projection. The reference patch, test patch, status lists and test command remain in an evaluator-only bundle, are mounted only for grading, and never enter the model prompt or agent workspace. Task commands execute in the digest-pinned Apptainer image with no host home/filesystem or network, using the fresh caller-owned ext3 `/testbed` image. Raw result material stays in the private run directory; only sanitized receipts and aggregate counts may be published.

The job uses one standard-tier B200, 8 CPUs, 128 GiB RAM and a 36-hour wall limit under `gpu_b200`. The run enforces a 200 GiB storage preflight, an 80 GiB single-file cap, and subsequent free-space floors after images, source exports and controls. Model assets and cache are removed on normal completion and caught failure, with cleanup recorded. A CUDA OOM terminates further model execution; every not-started assigned cell is explicitly retained as capacity-unknown so no denominator is silently changed. No second allocation or parallel account submission is permitted.

## Endpoint and decision rule

An episode is resolved only when it produces a nonempty patch and every declared F2P/P2P status is exactly `PASSED` under the pinned evaluator. A valid completed empty submission or a candidate patch that does not apply is graded unresolved. Other valid completed non-resolving episodes are also operational failures for this screen; setup, source/image, runtime, timeout-supervision, missing receipt, CUDA capacity, or incomplete-control failures are `UNKNOWN`, never model zeros. Each model arm must contain exactly one graded episode for each of the eight frozen task IDs. Any absent, repeated, malformed or ungraded cell makes the pair-level decision `UNKNOWN_INCOMPLETE_OR_UNGRADED`.

If and only if both denominators are complete, the provisional feasibility band is 15–85% terminal resolution in at least one model arm (for 8 rows, 2–6 resolutions). This band is a design feasibility screen, not an inferential threshold, task exclusion rule, population estimate, or evidence of model superiority. A result in-band means only `FEASIBLE_PAIR_FOR_NEXT_DESIGN_ONLY`. Otherwise the paired candidate is not accepted for that next design under this screen. Every count, raw receipt hash, missingness reason and arm denominator is retained; no selective reporting.
