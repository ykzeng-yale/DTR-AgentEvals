## Consolidated remaining experimental program

1. **Archive inference gate: concluded, no new assumption added.** The source-bound A6 report, exact branch-plan redraw, branch/source assumption inventory, finite-bound algebra, and current manuscript conclusion have been reconciled. Under available evidence, the fixed-benchmark Δ has a reproduced point estimate but no useful justified interval; execution dependence and recovery invariance are unknown/unavailable. Do not spend another cycle repeating this audit, fit policies on CONFIRM, or substitute an iid-task interval. Treat this gate as **not identified from the current archive** and carry it explicitly into the study limitation/design.

2. **Freeze one common-harness development executor pair and a family-level development frame.** Candidates must have pinned model revisions, artifact digests, licenses, tokenizers, dtype/quantization, runtime, common context/output caps, decoding, and a measured resource envelope. The pair must be screened on multiple development issues before being called competent; any task used for selection stays in development, and related issues remain in one repository-family split. Preserve operational exits and all assigned denominators. Require nondegenerate success in at least one arm, meaningful second-decision occupancy, and enough variation in observable feedback before training a router. A single passing task, the evaluator's 250 nested test IDs, or a successful import cannot satisfy this gate.

3. **Run the prospective DEVELOPMENT comparison only after gates 1–2.** Preserve the v2 treatment contract: model choice before logical call 1 and, if still eligible, before call 9; hold each choice for calls 1–8 or 9–24; common prompt, history, environment, caps, and strict endpoint. The primary pair compares frozen history-aware and prompt-only routers with the same initial small action and learner class. Include SS, SL, LS, and LL during development, and select the strongest fixed schedule using development data only. Randomize eligible assignments with the declared probability floor before each call; never redraw on transport retry or switch silently on fallback. Interleave policies and execution periods within task, seal the trajectory before independent grading, and keep evaluator/reference inputs outside model history.

4. **Establish precision on development executions before any final collection.** Use complete, prospective execution blocks on the fixed task list, with all task identities and zero/failed outcomes retained. The block vector must preserve shared task/log/fresh covariance and measured period effects. The current range-only Hoeffding guarantee is practically vacuous at plausible sizes; the replicated-block CLT/delta design requires independent, identically distributed blocks and validated operating characteristics. Use development-only repeated executions to estimate the relevant covariance and test the proposed interval in the matching simulator. Do not infer independence from RNG labels or task-family clusters alone.

5. **Freeze a practical decision threshold prospectively.** For a future H-versus-P terminal-resolution contrast, the lead selects a minimum worthwhile absolute success gain of **0.05**: one additional resolved task per 20 assigned tasks. Report success and resource vectors separately. A 95% interval with lower endpoint above +0.05 supports a meaningful gain; an upper endpoint below +0.05 rules out that minimum gain at that confidence level; an interval crossing +0.05 is inconclusive. This threshold is prospective only: it must not be retrofitted to archived outcomes, used to tune a router on CONFIRM, or represented as a new endpoint. No resource-saving/noninferiority claim is made without its own prospectively frozen loss margin and joint rule.

6. **Keep confirmatory collection held until the package is executable and reviewable.** Before any confirmation release, freeze task/family partitions, candidate pair and treatment digests, policies, endpoint, threshold, multiplicity, complete-block sampling and covariance method, numerical precision target, compute/total-resource caps, evaluator inputs, stopping/failure handling, and matching-simulator acceptance. All existing MBPP/HumanEval CONFIRM identities are permanently excluded from new tuning or confirmation. A new benchmark can be a separate study but cannot replace or be pooled with the original fixed target.

## Go/no-go and stopping rules

- **GO to a prospective DEVELOPMENT screen** only when the pinned pair, family-level task frame, public-only task path, common execution kernel, strict evaluator, complete receipts, resource caps, and independent cleanup are reviewed together in one exact release.
- **GO from development to a later confirmation design** only if the pair is genuinely nondegenerate, observable feedback creates consequential eligible decisions, and a design-specific precision analysis plus matching-simulator checks can answer the frozen +0.05 criterion within the declared resource budget.
- **STOP or narrow the claim** if no feasible competent pair exists, second-decision opportunity is too rare, the inference contract cannot be defended, or the required precision is infeasible. An unfavorable/null result is reportable evidence; no same-task retry, prompt/budget/cache tuning, selective task replacement, or outcome-triggered extension is allowed.

The next experiment is one consolidated, pre-outcome DEVELOPMENT competence screen (multiple issues, family-respecting frame, common pinned execution treatment, strict independent grader, complete operational outcomes), followed—only if that pair is competent—by the H/P development contrast and precision work.
